# 05 — SQLite, Relational Modeling & Idempotency

In data engineering, storing data is not just about writing rows to a disk; it is about designing constraints that maintain data integrity under retries, re-runs, and network interruptions.

---

## 1. What is Idempotency?

In mathematics and computer science, an operation is **idempotent** if applying it multiple times produces the exact same outcome as applying it once:

$$f(f(x)) = f(x)$$

### In ETL Pipelines:
If an ingestion pipeline runs at 10:00 AM and ingests 6 observations, running it again at 10:05 AM with the exact same raw data must **NOT** create 6 duplicate rows in your database.

```
Without Idempotency:
Run 1 ──> 6 rows inserted (Total in DB = 6)
Run 2 ──> 6 rows inserted (Total in DB = 12)  ❌ DUPLICATES CORRUPT METRICS!

With Idempotency:
Run 1 ──> 6 rows inserted, 0 updated (Total in DB = 6)
Run 2 ──> 0 rows inserted, 6 updated (Total in DB = 6)  ✅ DATA REMAINS ACCURATE!
```

---

## 2. Defining Natural vs. Surrogate Keys

- **Surrogate Key**: An arbitrary integer or UUID generated by the database (`id INTEGER PRIMARY KEY AUTOINCREMENT`). It has no business meaning and cannot prevent logical duplicates.
- **Natural Composite Unique Key**: A combination of real-world attributes that uniquely define a physical observation.
  - In our pipeline, an air quality observation is uniquely identified by **where** and **when** it was recorded: `(city, timestamp_utc)`.

```sql
CONSTRAINT uq_city_timestamp UNIQUE (city, timestamp_utc)
```

## 3. The SQLite Upsert Pattern

To achieve idempotency, `AQILoader` uses SQLite's `INSERT ... ON CONFLICT DO UPDATE` syntax (introduced in SQLite 3.24+):

```sql
INSERT INTO aqi_observations (
    city, state, zone, latitude, longitude,
    timestamp_local, timestamp_utc,
    pm2_5, pm10, carbon_monoxide, nitrogen_dioxide, sulphur_dioxide, ozone,
    provider_aqi, aqi_category, data_source, extracted_at_utc,
    created_at, updated_at
) VALUES (
    :city, :state, :zone, :latitude, :longitude,
    :timestamp_local, :timestamp_utc,
    :pm2_5, :pm10, :carbon_monoxide, :nitrogen_dioxide, :sulphur_dioxide, :ozone,
    :provider_aqi, :aqi_category, :data_source, :extracted_at_utc,
    datetime('now'), datetime('now')
)
ON CONFLICT(city, timestamp_utc) DO UPDATE SET
    pm2_5 = excluded.pm2_5,
    pm10 = excluded.pm10,
    carbon_monoxide = excluded.carbon_monoxide,
    nitrogen_dioxide = excluded.nitrogen_dioxide,
    sulphur_dioxide = excluded.sulphur_dioxide,
    ozone = excluded.ozone,
    provider_aqi = excluded.provider_aqi,
    aqi_category = excluded.aqi_category,
    extracted_at_utc = excluded.extracted_at_utc,
    updated_at = datetime('now');
```

---

## 4. Measuring Inserts vs. Updates

In `load.py`, before executing the upsert statement, the loader checks whether a row with `(city, timestamp_utc)` already exists. This enables exact accounting in our audit logs:
- `records_inserted`: Count of brand-new physical observations added to the database.
- `records_updated`: Count of existing observations refreshed or re-ingested.

## 5. ACID Transactions & Atomic Rollback

What happens if the pipeline crashes after writing 3 out of 6 records?
Without transactions, the database is left in a **partially written, corrupt state**.

In `load.py`, all batch writes are wrapped in an explicit SQLite transaction:

```python
with self.get_connection() as conn:
    try:
        conn.execute("BEGIN TRANSACTION;")
        for rec in records:
            conn.execute(upsert_sql, rec.to_dict())
        conn.commit()  # All succeed together
    except Exception as exc:
        conn.rollback()  # Any failure undoes all writes
        raise
```

- **Atomicity**: Either all 6 records are written, or none are.
- **Consistency**: Database constraints (unique keys, not-null rules) are never violated.
- **Isolation**: Concurrent readers cannot see half-written batches.
- **Durability**: Once committed, data is safely written to persistent disk storage.
